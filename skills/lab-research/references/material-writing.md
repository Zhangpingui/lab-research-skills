# 科研材料检索、论证与成稿

本流程把文献检索、研究事实和用户模板组织成可审查的材料。适用于国自然申请书、其他纵向申报、企业横向技术方案和研究报告；具体章节名称、字数和格式始终服从用户提供的当年模板。

## 一、建立材料契约

先识别：材料类型、读者/评审者、申报年份、目标章节、模板、篇幅、截止时间、引用格式、是否需要 Word、可使用的真实前期成果和禁止披露内容。缺失信息只在会改变结构或事实时集中询问，其他缺口进入 `missing-evidence.md`。

把输入拆成六类，避免在正文里混用：

1. `confirmed_result`：作者确认且有材料支持的前期结果；
2. `source_fact`：可定位的文献或指南事实；
3. `interpretation`：对材料的解释；
4. `hypothesis`：拟检验而未证实的判断；
5. `planned_work`：项目期内拟开展的工作；
6. `unknown`：需要作者、实验或检索补充的信息。

## 二、检索并建立证据账本

按 [文献检索流程](literature-search.md) 将立项依据、最接近工作、创新对照和方法可行性拆成独立检索任务。大型材料可以按技术主题并行检索，但去重、来源等级和主张 ID 必须由主流程统一。

每个拟写入正文的重要主张至少有一个状态：

```yaml
claim_id: C01
claim: "需要写入材料的判断"
claim_type: source_fact  # confirmed_result / interpretation / hypothesis / planned_work
sources: [R01]
support: partial
locator: "section/page/figure"
conditions: "数据、场景、比较对象和指标口径"
human_verified: false
```

没有证据的内容可以进入提纲，但要写成待验证假设或待补项，不能通过更肯定的语气掩盖缺口。

## 三、先构造论证，再写句子

将材料压缩成一条可检查的主线：

`领域需求/任务牵引 → 已有认识 → 未解决的具体缺口 → 科学问题或工程约束 → 拟议方法 → 判别性验证 → 预期知识增量或交付价值 → 适用边界`

每个章节先做反向提纲：章节目的、每段唯一任务、段落主张、支撑证据和与下一段的逻辑关系。文献综述按技术路线、关键假设和失效条件综合，不按年份或论文逐篇堆砌。段落开头尽量说明该段要证明什么，后续句子通过原因、对比、证据、限制或结果与其连接。

不同材料强调不同：

| 类型 | 核心论证 |
|---|---|
| 国自然 | 科学问题、可检验假设、知识增量、证据与可行性 |
| 其他纵向 | 指南任务、研究内容、考核指标、组织实施和风险 |
| 企业横向 | 需求边界、接口、技术路线、交付物、测试与验收 |
| 研究报告 | 问题、依据、分析过程、结论、局限和建议 |

## 四、分节起草与语气控制

从证据账本向外写作，不从空白页自由扩写。每个重要结论尽量靠近支持它的文献、数据或比较。根据证据强度选择“表明、支持、提示、可能、拟验证”等动词；不使用无范围的“首次、国际领先、彻底解决”。

大型任务可以采用三种相互隔离的角色：检索者只返回来源和证据，起草者只使用通过闸门的账本，审查者检查引用语义、跨章节一致性和竞争解释。主流程负责最终取舍，不把三个角色的文本直接拼接成申请书。

## 五、一致性和反证审查

交付前检查：

- 题目、摘要、科学问题、目标、研究内容、技术路线和验证是否对应；
- 已完成、拟开展和预期结果是否用词清楚；
- 引用是否真的支持对应句，且年份、DOI、作者和版本一致；
- 创新点是否对照最接近工作并写清差异，不把“组合模块”自动等同于创新；
- 指标、数据集、场景、期限、术语和资源是否前后一致；
- 是否存在能同样解释预期结果的竞争解释，以及区分它们的对照。

## 六、推荐交付包

- `search-plan.md`、`references.json`、`claim-evidence.json`；
- `argument-map.md`：章节—段落—主张—证据映射；
- `proposal-draft.md` / `technical-proposal.md` / `research-report.md`；
- `missing-evidence.md`：只保留会影响判断或定稿的缺口；
- 用户要求 Word 时，按 [Word 交付](word-delivery.md) 生成 `.docx` 和 QA 记录。

默认同时交付可编辑正文和简短审查说明。审查说明不要混入正式材料正文。
